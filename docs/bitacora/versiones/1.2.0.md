# 1.2.0 — Daemon de Laya, compuerta determinista y quién decidió

- **Fecha**: 2026-10-03 · **Commit**: `24c450b` (del espejo agent-plugin-synapse) · **Tipo**: feat
- **Visto en**: diseño (`test_project_scope.py` modela un repo con worktrees anidados, como klinikae)

## Síntoma

- Latencia mediana de unos 6 s por hook: cada uno importaba torch y cargaba el modelo.
- Un `block` o un `ask` no decía si venía de una regla o de Laya.
- El alcance del proyecto fallaba con worktrees y superproyectos.

## Causa

- Laya corría dentro del proceso del hook.
- Lecturas, archivos de credenciales y líneas sin secretos llegaban a Laya sin necesidad.
- La raíz del proyecto no se obtenía del entorno git de `CLAUDE_PROJECT_DIR`.

## Cambio

- `hooks/laya_daemon.py`: daemon persistente en un socket Unix, inferencia serializada y apagado por inactividad;
  los hooks ya no importan torch. Latencia de unos 70 ms (inferencia p50 de unos 30 ms).
- Primero lo determinista: pipelines de solo lectura, archivos de credenciales, usos de `.env` y líneas candidatas
  a secreto. FPR de 0.30 % a 0.15 %, recall de 81.35 % sin cambio y 28 % menos consultas a Laya.
- Alcance desde git (toplevel, superproyecto, worktrees); variables de shell resueltas; tocar `.git` pide `ask`.
- Mensaje `Synapse · <hook> (python|laya) · regla <rule>`; la traza guarda `decided_by`, `rule`, `reason` y evidencia.
- Reglas nuevas: `kill -1` (block); docker privilegiado o con la raíz del host y `http.server` sobre home o `/` (ask).
- Retención de logs de 30 días, una sola escritura con lock por línea y `scripts/benchmark.py`.

## Prueba

`test_laya_daemon.py`, `test_laya_daemon_gpu.py`, `test_deterministic_gate.py`, `test_attribution.py`
(`test_every_block_and_ask_says_who_decided`) y `test_project_scope.py`; casos `block_kill_all_processes*`,
`ask_docker_*`, `ask_http_server_serving_*` y `ask_git_dir_*`.

## Lección

Cada decisión debe nombrar quién la tomó y con qué regla: sin eso no se puede depurar un falso positivo.
