# 1.0.0 — Primeros guardrails PreToolUse como plugin

- **Fecha**: 2026-10-01 · **Commit**: `da97e8d` (del espejo agent-plugin-synapse) · **Tipo**: feat
- **Visto en**: optical-soft (los cuatro hooks reemplazan a los de `optical-soft/.claude/hooks/`)

## Síntoma

En sesiones con Claude Code había confirmaciones constantes para borrar temporales de `./tmp/`, lecturas de
`.env` completos que volcaban tokens al contexto, claves reales escritas en código y cambios accidentales en
lockfiles o en `.git/`. Los guardrails vivían como scripts sueltos dentro de un proyecto.

## Causa

No había una capa común: cada proyecto copiaba sus hooks, que no se podían reutilizar ni probar por separado.

## Cambio

- Plugin `claude-plugin-synapse` con cuatro hooks `PreToolUse`:
  - `block_dangerous` (Bash): `allow` para temporales y artefactos de build, `block` para comandos catastróficos
    (`rm -rf /`, fork bomb, `mkfs`, `dd`, force push a `main`), `ask` para borrar código permanente.
  - `block_env_read` (Bash, Read): bloquea la lectura de `.env` y muestra solo las claves con tipos inferidos.
  - `detect_secrets` (Edit, Write): firmas `sk-*`, `AKIA*`, `ghp_*`, JWT y contraseñas; admite placeholders.
  - `protect_files` (Edit, Write): `.git/`, `.venv/`, `.env` y lockfiles; `ask` para `.claude/settings.json`.
- Clasificador Laya System 1 (GPU/CPU) con degradación a reglas deterministas si no hay torch.
- Comando y skill `synapse-status`, regla `security-guardrails.md` y log en `~/.claude/logs/security_hooks.log`.

## Prueba

`tests/test_hooks.py` (32 pruebas según el README) y `tests/test_manifest.py`.

## Lección

Llevar los guardrails a un plugin los vuelve una pieza versionada y con pruebas, en lugar de una copia por proyecto.
