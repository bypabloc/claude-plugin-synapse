# 1.4.0 — Sincronizar lockfiles no pasa por Laya

- **Fecha**: 2026-10-08 · **Commit**: `a2d79b2` (del espejo agent-plugin-synapse) · **Tipo**: feat
- **Visto en**: No consta en la historia (`uv lock --directory <proyecto>/server`)

## Síntoma

`uv lock --directory <proyecto>/server` recibió un `ask` (`laya.danger`, score 0.990 ≥ 0.952), aunque la evidencia
decía que el comando era de solo lectura.

## Causa

Con evidencia de solo lectura, el score salió solo de las palabras del comando. La sincronización de lockfiles no
tenía una regla determinista y siempre llegaba al modelo.

## Cambio

`is_lockfile_sync()` resuelve sin Laya `uv lock|sync` y `bun|pnpm install` cuando no nombran paquetes, no son
instalaciones globales, todas las rutas quedan dentro del proyecto y solo redirigen a `tmp/`. Combinarlos con
subcomandos de lectura (`cd`, `tail`) se acepta. `uv add`, `uv run`, `bun install <pkg>` y cualquier otra cosa
siguen llegando a Laya.

## Prueba

`tests/unit/test_deterministic_gate.py`: `test_lockfile_sync_skips_laya` (`uv lock`, `uv sync --all-groups`,
`cd server && uv sync --frozen`, `pnpm install`…), `test_lockfile_sync_with_absolute_directory_inside_project_skips_laya`
y `test_package_changes_still_reach_laya` (`uv add requests`…).

## Lección

Un score alto con evidencia neutra es una señal de que el modelo reacciona al vocabulario: ese comando necesita
una regla, no un umbral más alto.
