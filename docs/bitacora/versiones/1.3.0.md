# 1.3.0 — Borrar lo que git puede restaurar se aprueba solo

- **Fecha**: 2026-10-07 · **Commit**: `9b314fe` (del espejo agent-plugin-synapse) · **Tipo**: feat
- **Visto en**: No consta en la historia

## Síntoma

Borrar archivos o directorios versionados sin cambios locales pedía confirmación, aunque git los recupera. La
primera versión de la regla (`478a7a5`) dejaba huecos por donde se podían perder datos.

## Causa

- No se distinguía entre contenido recuperable por git y trabajo sin guardar.
- En esa primera versión, `rm -rf link/` sobre un symlink versionado podía borrar fuera, cualquier contenido
  ignorado contaba como regenerable y un comando compuesto aprobaba subcomandos que no eran borrados.

## Cambio

- Regla `structure.git_recoverable_delete`: borrar archivos o directorios versionados y limpios se aprueba, y la
  sesión recibe en `additionalContext` cómo restaurarlos.
- Se excluyen los repos con `.git` propio y los archivos `skip-worktree` o `assume-unchanged`.
- `rm -rf link/` sobre un symlink versionado ya no se aprueba solo.
- Solo las cachés de intérpretes cuentan como contenido ignorado regenerable.
- Un comando compuesto con subcomandos que no son borrados vuelve a `ask`.
- La pista de restauración usa `git -C <dir>` con rutas absolutas.

## Prueba

`tests/unit/test_git_recoverable.py`: `test_recoverable_delete_allows_with_checkout_hint`,
`test_recoverable_delete_not_auto_allowed`, `test_recoverable_hint_restores_after_cd`,
`test_git_recoverable_targets` y `test_repo_root_is_not_recoverable`.

## Lección

Un auto-allow por recuperabilidad tiene que probar que todo lo borrado es recuperable: symlinks, ignorados y
comandos compuestos son las vías por donde se pierde trabajo.
